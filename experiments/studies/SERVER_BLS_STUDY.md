# Automatic BLS server experiment (24-worker cap)

This branch adds a **single command** to calibrate the server, size/create a BLS input dataset if necessary, and run a complete, resumable experiment. It uses the existing Rust benchmark engine, SQLite collection, `perf`, Python campaign runner and statistical report generator. **It does not start any measurements until dataset preparation succeeds.**

## Setup

Linux, Python 3.11+, Rust/Cargo, git, lscpu and perf are required. Cargo fetches the pinned Threadance Git dependency from GitHub on the first build. Run **--check** on any development machine without calibration. For **--plan-only** and the full experiment, use a **regular user** on the 24+-CPU server who is allowed to access `perf stat -e task-clock`; the script does not run sudo or modify the kernel. A quiet/dedicated machine with >=24 allowed logical CPUs is recommended. Check CPU topology, NUMA, SMT and thermals before interpreting results.

```bash
mkdir -p ~/benchmarks
cd ~/benchmarks
git clone https://github.com/igorbologovv/thread_pool_harness.git
cd thread_pool_harness
git switch experiment/bls-server-24w-autoprep

bash run-server.sh --check      # static matrix validation (also works on 16-CPU laptop)
bash run-server.sh --plan-only  # server only: calibrates CPU and freezes a plan
bash run-server.sh              # starts or resumes all campaigns
```

## Exactly what happens

1. Check Git cleanliness, CPU allowance and unprivileged perf access. Set `RUSTFLAGS=-C target-cpu=native`.
2. Find a compatible **scheduler-free BLS service-time calibration** (200 WU); if absent, generate its small dataset and record 50 calibration runs after 10 warmups.
3. Use scheduler-free service time only as a **conservative sizing estimate** for a dataset and per-worker work-unit counts: initial rate estimate = `rho * workers * 1e6 / S`. The initially generated workload contains at least `ceil(0.2 * estimated_max_rate * 1.2) + 1` work units; the 20% reserve targets arrival windows of >=200ms. This **estimate is not the paced load reference**.
4. Select a **shared dataset of at least 6000 distinct BLS certificates**, rounded upward if a faster server requires more. Existing exact caches are reused and verified using the deterministic header and SHA-256; absent caches are generated by the existing Rust harness before any measurements. The script enforces a 100000-certificate limit and refuses to overwrite corrupted existing cache files without review.
5. First execute the **seven saturated all-at-once campaigns**, average measured throughput across the six schedulers at each worker count to obtain the shared reference `Cw`, then create the **14 paced campaigns** with `lambda = rho * Cw`. If measured Cw requires a larger dataset or longer paced run, size it up and generate it before paced measurements. References are saved in `definitions/saturation_references.json`. The new optional `saturated_reference_wu_s` field in paced TOMLs preserves `rho` and the measured normalization; legacy campaigns are unchanged. Runs use existing `prepare`, `collect`, `resume`, and `analyze` machinery, and a failure leaves earlier results intact.
6. Generate `study_report.html` and `study_report.json` after all campaigns are complete.

## Experimental matrix

- **Workers:** 2, 4, 8, 12, 16, 20, 24.
- **Schedulers:** Rayon, Bevy, MPMC Spin(0), MPMC Agave, RTRB b1, RTRB b2.
- **Modes:** all-at-once, fixed-arrivals, bursty-arrivals.
- **Paced offered-load levels:** 25%, 30%, 35%, ..., 95%, inclusive (15 levels).
- **Per condition:** 40 randomized blocks, **4 warmups per invocation**, 2 measured repetitions. Two custom perf passes: standard (`task-clock`, `cycles`, `instructions`, `context-switches`, `cpu-migrations`, `branch-misses`) and cache (`task-clock`, `cache-references`, `cache-misses`), with reversed pass order in alternating blocks.
- **BLS work:** 2000 validators, 1600 signers, 1 certificate/WU, input seed 1.
- **Total:** 1302 distinct conditions, 52080 invocations, **208320 measured physical runs** across the two perf passes, plus warmups.

At 2 workers fewer unique WU are executed than at 24 workers. All campaigns use the same deterministic dataset; every single run verifies distinct certificates, but the same certificate set can be reused across runs.

## Logs and data

All progress is streamed to terminal **and** `results/studies/bls-server-24w/server-run.log`, with explanations for calibration, rate selection, dataset reuse/generation, each campaign, resume and reporting. Raw data, logs, per-campaign plans and environment metadata are stored under `results/studies/bls-server-24w/campaigns/`. The frozen definitions, measured saturated-throughput references and size calculations are in `results/studies/bls-server-24w/definitions/`. In `--plan-only` mode, only preliminary all-at-once definitions are generated; paced rates are not fixed until saturation has been measured.

There is **no** automatic CPU pinning. Run only on a reserved server without competing workloads. Also, tests across different CPUs must be analyzed as separate experimental platforms. The report does not independently validate the thesis's automatic configuration selector; this requires additional common absolute-rate experiments. The workload can be very large, so inspect `--plan-only` and check free disk space and CPU time before launching. For SSH sessions, use `tmux` or a batch scheduler; the script itself is not a background daemon.
